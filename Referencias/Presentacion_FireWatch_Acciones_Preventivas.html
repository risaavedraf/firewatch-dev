Propósito y progreso

Valor de FireWatch

De una señal territorial a una revisión que deja registro

Base construida

Consulta y procesamiento

  • API protegida para consultar el último lote, el historial y el estado de trabajos.
  • Panel conectado al gateway, con consulta de lotes y solicitud administrativa de una demo.
  • Procesamiento asíncrono con eventos, persistencia y auditoría del trabajo.
Flujo validado

Decisión humana y seguimiento

  • Combinar una lectura orientativa con exposición y preparación del sector.
  • Revisar la sugerencia: aceptar, ajustar o rechazar con el motivo.
  • Seguir la acción mediante responsable, plazo, estado, evidencia y revisión posterior.

La propuesta complementa el mapa con trazabilidad: una clasificación orienta la revisión, no se transforma en una orden automática.

Acceso y consulta

Panel → Gateway → Risk

El panel inicia sesión con Keycloak; el gateway verifica el token y enruta consultas protegidas del lote reciente y su historial.

Jobs + eventos

Flujo preventivo validado

Funcionamiento de la propuesta

Siete etapas conectan datos, prioridad y seguimiento

01 · Datos

Integrar y revisar

Antecedentes históricos, meteorológicos y territoriales con fuente, fecha, cobertura y calidad disponibles.

02 · Lectura

Clasificar el sector

Nivel orientativo, período, vigencia y versión; indicar información insuficiente cuando corresponda.

03 · Contexto

Considerar exposición

Leer por separado el riesgo estimado, la exposición local y la preparación del sector.

04 · Prioridad

Ordenar la revisión

Usar la lectura territorial y su contexto para identificar dónde conviene revisar primero.

05 · Sugerencia

Proponer una acción

Vincular una orientación preventiva al sector y explicar el motivo, sin ejecución automática.

06 · Decisión humana

Aceptar, ajustar o rechazar

Una persona facultada decide y deja registrado el motivo.

07 · Seguimiento

Documentar y revisar

Registrar responsable, plazo y estado; vincular evidencia y una lectura posterior independiente.

La prioridad orienta una revisión humana; no es una orden ni una predicción exacta de ignición.

Roles de la arquitectura objetivo

Responsabilidad y seguimiento del flujo validado

El seguimiento conserva quién decidió, qué se hizo y cómo se revisó

Viewer

Consulta

Revisa sector, nivel orientativo, vigencia, factores e historial disponible.

Admin

Administración

Admin gestiona datos, revisa métricas, aprueba versiones y administra acciones, con registro de auditoría.

Revisión humana

Decide y fundamenta

La persona facultada acepta, ajusta o rechaza la sugerencia; la decisión y su motivo quedan registrados.

Estado
Pendiente, en curso, completada, rechazada o vencida; cada cambio conserva autor y fecha.
Evidencia
Se adjunta o referencia y una persona revisora comprueba su suficiencia según el criterio de la acción.
Reevaluación
La lectura posterior se registra aparte; puede mantener, reducir o aumentar la prioridad.

La evidencia ayuda a verificar la ejecución; no demuestra por sí sola una disminución del riesgo.

Arquitectura objetivo validada

Contenedores y conexiones

El diseño integra actores, datos, procesamiento, modelo y mapa

Personas y web

Viewer / Admin

Viewer consulta el mapa, vigencia e historial. Admin gestiona datos, versiones, métricas y acciones preventivas.

Interfaz y API

Web + REST/HTTPS

React, TypeScript y MapLibre presentan el mapa; Go/Gin gestiona consultas, permisos y coordinación asíncrona.

Datos y modelo

Procesar e inferir

Históricos CONAF y variables DMC/NASA alimentan Python/scikit-learn; Go/ONNX ejecuta el modelo aprobado por lotes.

Persistencia y contexto

Datos versionados

Oracle Autonomous Database conserva usuarios, resultados y auditoría; Object Storage guarda conjuntos y modelos. Un proveedor aporta cartografía.

Esta vista describe la arquitectura objetivo; la implementación actual de Gateway, Risk, Jobs y panel se presenta en las diapositivas 3–5.
