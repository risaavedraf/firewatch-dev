# Kubernetes deployment base

This is a staging deployment template for the **synthetic backend slice**, not a provisioned production environment. Compose remains the local development path. The manifests provide two replicas per service, probes, resource limits, restricted containers, disruption budgets, TLS ingress and network policies.

## Configure before applying

1. Select the target cluster, registry, ingress controller and real DNS names. Replace all `replace-before-deploy` image tags with reviewed immutable digests using a Kustomize overlay.
2. Provision PostgreSQL/PostGIS and RabbitMQ with persistence, backups and TLS. This implementation uses PostgreSQL-specific SQL. Oracle production compatibility is **not** implemented; confirm the production database decision separately.
3. Configure an OIDC realm with RS256 access tokens, `firewatch-api` audience and `realm_access.roles` containing `viewer`/`admin`. Use Authorization Code + PKCE for a future browser client. The local password-grant client and demo accounts are not production identity configuration. **The realm is provisioned out of band, not by these manifests**: the only realm file in the repository is the development one, whose `${DEMO_ADMIN_PASSWORD}`, `${DEMO_VIEWER_PASSWORD}` and `${DIRECTORY_CLIENT_SECRET}` placeholders no Secret here supplies, so `bootstrap-secrets.sh` renders that file as the `keycloak-realm` ConfigMap and no Deployment mounts or imports it. A Keycloak that answers with no `firewatch` realm after its pod starts is therefore the expected state and not a silent failure: the realm appears when this step is done. The provider's first administrator, which is what creates it, comes from the `keycloak-bootstrap-admin` Secret in step 4.
4. Create the namespace and provision the bootstrap material with `deploy/k8s/bootstrap-secrets.sh`, or through the target secret manager using the next two tables as the key contract. The script creates every Secret in the first table except `firewatch-tls`, and every ConfigMap in the second. It never rewrites a Secret that already exists: a generated password or certificate is reused on each run, because replacing it under a running service breaks that service at its next reconnect. To rotate deliberately, delete the Secret, re-run, and restart the workloads that mount it. The ConfigMaps carry repository files and are re-applied on every run, which is safe: they are read at container start and hold no decision of their own.

| Secret | Keys |
|---|---|
| `jobs-runtime` | `DATABASE_URL` (jobs_app, TLS `sslmode=verify-full`), `AMQP_URL` (`amqps://` on 5671, user `firewatch-jobs`, vhost `firewatch`) |
| `risk-runtime` | `DATABASE_URL` (risk_app, TLS `sslmode=verify-full`), `AMQP_URL` (`amqps://` on 5671, user `firewatch-risk`, vhost `firewatch`) |
| `prevention-runtime` | `DATABASE_URL` (risk_app, TLS `sslmode=verify-full`; the frozen contract puts the `prevention` schema inside the shared risk database, so this key points at that same database and not at one of its own) |
| `postgres-credentials` | `POSTGRES_PASSWORD`, `JOBS_DB_PASSWORD`, `RISK_DB_PASSWORD`, `KEYCLOAK_DB_PASSWORD` |
| `broker-credentials` | `RABBITMQ_PASSWORD`, `RABBITMQ_JOBS_PASSWORD`, `RABBITMQ_RISK_PASSWORD`, `RABBITMQ_ERLANG_COOKIE` |
| `migration-credentials` | `JOBS_DATABASE_URL`, `RISK_DATABASE_URL` for the migration-owner Jobs (TLS `sslmode=verify-full`); never mounted by an application Deployment, because a migration owner can reshape the schema |
| `keycloak-bootstrap-admin` | `KC_BOOTSTRAP_ADMIN_USERNAME`, `KC_BOOTSTRAP_ADMIN_PASSWORD`: the identity provider's first administrator, both generated. Keycloak reads them only on a first start against an empty `identity` database; afterwards the account lives in that database and the Secret is not read again. Without an administrator no realm can be created at all, so this is the one Secret here whose value an operator has to read out of the cluster (`kubectl --namespace firewatch get secret keycloak-bootstrap-admin -o yaml`) before the realm of step 3 exists |
| `firewatch-ca` | `ca.crt` only. The signing key stays on the operator's machine (`FIREWATCH_CA_KEY`): anything able to read Secrets could otherwise mint a certificate for any service here and answer as it |
| `postgres-tls`, `rabbitmq-tls`, `gateway-tls`, `jobs-tls`, `risk-tls`, `prevention-tls`, `inference-tls`, `keycloak-tls` | `tls.crt`, `tls.key`, `ca.crt`: one server certificate per service, issued by the internal CA |
| `firewatch-tls` | Ingress certificate and private key. **Not** created by `bootstrap-secrets.sh`: it certifies the public DNS name, which the repository does not own, so the operator supplies it |

Each server certificate carries the name of the Service its clients dial (`gateway`, `jobs`, `risk`, `prevention`, `inference`, `rabbitmq`, `postgres`, and `identity` for Keycloak, whose Secret is `keycloak-tls`) as a SAN, because that is the name an in-cluster client marks when it verifies the host.

| ConfigMap | Key | Repository file it carries |
|---|---|---|
| `postgres-init` | `postgres-init.sh` | `deploy/local/postgres-init.sh`, mounted by the PostgreSQL StatefulSet |
| `rabbitmq-plugins` | `enabled_plugins` | `deploy/local/rabbitmq-plugins`, the file `RABBITMQ_ENABLED_PLUGINS_FILE` names |
| `rabbitmq-topology` | `rabbitmq-topology.sh` | `deploy/local/rabbitmq-topology.sh`, run as the `broker-provision` Job's entrypoint |
| `keycloak-realm` | `firewatch-realm.json` | `deploy/local/firewatch-realm.json`, the development realm. Rendered but **not** mounted and **not** imported, for the reason in step 3 |
| `inference-model` | `logistic.json` | `services/inference/testdata/logistic.json`, byte for byte the file the Compose stack mounts. The inference Deployment mounts the ConfigMap read-only at `/models`, so its single key lands at `/models/logistic.json` — the path `FIREWATCH_MODEL_PATH` names |

The inference artifact travels as a ConfigMap rendered by the script rather than a `configMapGenerator`, because the base's load restrictor refuses a generator file outside the kustomization root and copying the model into `base/` would give the repository two models that can drift. The volume is not `optional`: without the ConfigMap the pod stays in `CreateContainerConfigError`, and a pod whose mounted file is missing or unreadable stops at startup naming `FIREWATCH_MODEL_PATH` instead of answering from a model nobody loaded.

5. Create `jobs_app` and `risk_app` roles and separate databases. Run each corresponding application image with argument `migrate`, a migration-owner `DATABASE_URL`, and a bounded Kubernetes Job **before** deploying replicas. SQL migrations are transactional and serialized by advisory lock. PostGIS extension installation needs suitable DBA permissions. Never pass migration-owner credentials to application deployments. The prevention service shares the risk database and owns the `prevention` schema inside it: run its `migrate` Job against that same database as well, and let `009_preventive_actions.sql` create the schema and the grants of the unprivileged application role; `011_preventive_evidence.sql` adds the evidence table. Both take the next versions of the database's `schema_migrations` ledger (`009` after the risk `008`, `011` after the risk `010`), so the prevention `migrate` Job must run after the risk one.
6. Adapt `network.yaml` to your DNS, monitoring, ingress and infrastructure namespace labels; managed external databases require explicit egress IP rules. The initial port-443 egress rule is intentionally broad until the identity provider is selected. An enforcing CNI is required. The services no longer declare broker topology: provision the two publish exchanges (`firewatch.jobs.events`, `firewatch.risk.events`), the shared direct `firewatch.dead` exchange, the four queues (`risk.jobs.v1`, `jobs.results.v1` and their `.dead` companions) and the five bindings between them, with `deploy/local/rabbitmq-topology.sh` as the reference shape. Grant each service identity `configure` on its own exchange and queues, `write` on its own publish exchange only, and `read` on its own queue only; no service gets `write` on `firewatch.dead`, because the broker dead-letters and that grant would let one service forge a dead letter into its peer's queue. Neither identity carries a management tag, so the management API stays with an operator identity. Locally, Compose derives both service passwords from the single RabbitMQ secret it already requires, so one secret backs three identities (`firewatch`, `firewatch-jobs`, `firewatch-risk`); production needs one secret per identity.
7. Render with `kubectl kustomize deploy/k8s/base`, then validate your overlay against the target cluster before applying it.

## Running the bootstrap on Windows

`bootstrap-secrets.sh` is written for a POSIX host and is what CI and any Linux operator runs. On Git Bash/MSYS it needs two workarounds, both about path translation rather than about the script's logic:

- `mktemp -d` returns a POSIX path such as `/tmp/tmp.XXXX`, which neither the mingw build of `openssl` nor the native `kubectl.exe` can open. The script then dies at the CA step **without a message**, because each `openssl` call silences its own stderr under `set -eu`. Put a `mktemp` shim first on `PATH` that prints a Windows-shaped directory (`cygpath -m "$TEMP"/...`) so both binaries agree on the same path.
- MSYS also rewrites a `-subj "/CN=..."` argument into `C:/Program Files/Git/CN=...`, which corrupts the certificate subject. `MSYS_NO_PATHCONV=1` fixes that, but it simultaneously stops the `--from-file=...=/posix/path` arguments of the ConfigMap step from resolving. The two settings cannot be active in the same run: issue the certificates with `MSYS_NO_PATHCONV=1`, then re-run with translation enabled, which skips the certificates because they already exist and lets the ConfigMaps land.

Neither issue can appear on the Linux runners this project targets, so treat them as host constraints, not defects: nothing in the manifests or the script changes for them.

## Operational boundaries

- The services never declare topology: at startup each only checks its own exchange and queues passively and fails naming the missing resource, so a missing exchange or queue is a broker provisioning fault rather than an application one. Bindings are not visible to a passive check: a missing or renamed binding stays silent at startup and surfaces later as unroutable publishes.

- OIDC issuer and JWKS endpoints must use HTTPS outside `APP_ENV=development`.
- Internal traffic between the application pods is TLS: each Deployment mounts its own `<service>-tls` Secret at `/etc/tls` and sets `TLS_CERT_FILE`, `TLS_KEY_FILE` and, where the service calls a peer, `TLS_CA_FILE`. A pod without that material refuses to start under `APP_ENV=staging` instead of serving in clear, which is the startup guard doing its job. The gateway's upstreams are `https://` and its own Service is HTTPS-only, so the ingress controller in front of it must be told the backend speaks TLS (`backend-protocol: HTTPS`, task T8). Network policies still carry the isolation, and mTLS was considered and not chosen: service identity already travels in the bearer token and, for the broker, in the AMQP user.
- Gateway readiness reports its own availability; service readiness checks PostgreSQL. Broker loss deliberately does not remove read APIs from service: existing batches remain available and commands use the outbox.
- Quorum queues on a single local RabbitMQ node are durable, not highly available. Production needs an appropriately sized multi-node broker or a managed offering.
- A redelivered message that exhausts its five attempts is no longer left silently `queued`: the `jobs` consumer records `attempts`, `failure_reason` and `failed_at` and moves the row to `failed` (`services/jobs/migrations/004_job_failure_state.sql`), fed by the `risk.job.failed.v1` event that `risk` emits (`ReportFailure`, `services/risk/cmd/server/main.go:215`; consumed by `Fail`, `services/jobs/cmd/server/main.go:130`). An operator returns a failed or explicitly confirmed `queued` job to `queued` through `POST /v1/jobs/{id}/replay`. Dead-letter queues still need inspection for messages that cannot be decoded, and automatic replay tooling remains later work.
- Deployment replicas are not evidence of a measured availability SLA. Cluster rollout, failover, restoration, mTLS, external secret integration and load targets still require environment-specific validation.
