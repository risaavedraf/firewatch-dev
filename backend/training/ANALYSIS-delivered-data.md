# Analysis of the delivered data

This report is generated by `backend/training/analyze_delivered.py` and committed,
the same way `REPORT-delivered-data.md` is. Its inputs are the three untracked
files under `data/`, so it is not rebuilt in CI; re-run

    python backend/training/analyze_delivered.py

and diff. A hand edit is a defect, not a shortcut: every number below is computed
from the bytes in the table under it.

**What this is not.** It is not the model comparison. `train_delivered.py` already
trained two models on the dashboard and measured them against two baselines, and
`REPORT-delivered-data.md` is that measurement. This report asks the prior
question, file by file: what each delivered file contains, what it cannot support,
and which concrete dataset feature would fix it.

matrix gives 0.888 between the climatology columns and 0.653 / 0.612

0.954 / 0.943. The bytes are the authority here; the
difference is reported rather than smoothed over.

### Verdict

**Verdict: this file locates fires in time at region granularity and nothing finer.**
It provides a defensible region-day label (the counter's advance) at a complete 16 x 90 grid, and 5 other numeric columns that mostly restate how far into the season the calendar has moved. It cannot answer a question about a comuna, a weather day or an individual fire, and at this resolution the only thing it can teach a model is the season. `REPORT-delivered-data.md` records what that was worth.

### The identifier chain: `com_ia_id` -> CUT

2. the region part must be 01..16 and the comuna part must not be 000;
3. the region label must agree with the region part;
4. the comuna must exist in the tracked DPA layer, for the two regions that

**Radiation.** 4 readings sit above the solar constant of 1361
W/m2, at 326 (La Serena): 1713.67, 1758.00. Surface global irradiance cannot
exceed the irradiance at the top of the atmosphere, so these are sensor or scaling
errors, whatever the timestamp says.

**Humidity.** 1 reading sits at exactly 0.00 %, at 120 (Tierras Nobles). A relative humidity of 0.00 % is not a measurement a coastal station makes; it is the floor a sensor reports when it has nothing to report.

**Pressure.** No reading falls outside the declared physical bound, and the lowest is 593.03 hPa at station 145 (Lago Chungará), at -18.281824000, -69.138499833. The standard atmosphere reaches that pressure at about 4295 m, which is what the coordinates imply for the altiplano: it is a plausible **station** pressure, not a defective one. The defect is the missing elevation column and the missing reduction convention -- in one column, a station at 4 000 m and one at sea level cannot be compared.

**Evapotranspiration.** 290 of 292 readings sit outside a daily ET0 bound, with a maximum of 686.778. The column declares no unit and no period, and a value in the hundreds is an accumulated quantity, not a daily one: it cannot be used until the aggregation is declared.

**Derived quantities.** `GRADOS_DIA` runs 0.000 to 0.520; `HORAS_FRIO` runs 0.000 to 1.000. A daily cold-hours total that never exceeds one, and a degree-day total that never exceeds one either, are not daily totals in the units their names claim; the aggregation is undeclared and the columns are unusable as they stand.

**Zero is a measurement here.** 431 precipitation readings are exactly zero, and that
is a fact about the weather, not a floor. Counting values at a bound is only evidence of
a floor when the bound is physically unreachable, which is why the humidity row is
called out and the precipitation row is not.

### The single timestamp

Every row carries the same `rtd_dt_marcatiempo`: 2026-09-28 09:00:00.000 -0300. One
instant is not a day, so `TEMP_MAX`, `TEMP_MIN` and `PRECIPITACION` cannot be daily
aggregates here, whatever the column names say -- they are one reading each. The
snapshot is a picture of the network at 09:00, and the widest a station gets is
1 instant for its station-day.

The artifact's declared maximum for `radiation_sol` is

the table above is the check that works, and it is the one the artifact should carry.

Where the snapshot is internally consistent, say so: every station reporting
`TEMP_MIN`, `TEMP_MED` and `TEMP_MAX` keeps them ordered
(0 violations), so the failure here is not the
temperature column.

### Verdict

**Verdict: `rtdata` is one instantaneous cross-section of the network, and it cannot
support a daily label or a daily feature.** It shows which stations were reporting
at one instant and with what values; it carries a single timestamp, no quality flag
on any row, no unit for any variable, and 1,437 extra rows for 3,685 observations.
2 derived variables (`GRADOS_DIA`, `HORAS_FRIO`) have undeclared aggregation, and 4 of its 5122 readings exceed the solar constant. What survives is a snapshot that can be used to test a parser, never to train a model.

## 4. The cascade: what the product needs and which file supplies it

One row per property the model's input needs. A `no` is a measured absence: the
count next to it is the column, row or timestamp count that decided it.

| Property | `dashboard_conaf` | `emas` | `rtdata` | What would supply it |
| --- | --- | --- | --- | --- |
| A daily weather value for a comuna-day | no -- 0 weather columns of 10 | no -- station metadata, no reading | no -- 1 instant, at most 1 reading per station-day | hourly readings over every civil day for a point in each comuna, or a daily aggregate with a declared day boundary -- 7 variables |
| Weather on days without a fire | no -- the file has no weather at all | no | no -- one day, and it is not a labelled one | an archive that carries quiet days; `meteo.py` already fetches two of them, which is the only part of this need the repository can meet today |
| A fire event with a date and a comuna | no -- 16 region labels, no comuna, no event identity | no -- a station is not an event | no | an event-level registry keyed by comuna CUT with a local date; the access-gated CONAF product the plan's Log L5 identifies is the only source the log names |
| Station coverage per comuna | no | yes -- 535 stations over 235 comunas, with 23 rows whose region label and CUT disagree | yes for this instant -- 437 stations | the post-2018 CUT on every row, and an active station in the 12 Valparaíso comunas that have none |
| A quality flag per reading | no -- no flag column | station level only -- 437 active, 98 inactive | no -- 5 columns are empty on every row, including both flag columns | a per-reading quality code with a documented code set, and a rule for what an absent flag means |
| A declared unit and a station elevation | no unit declared; the quantities are counters | no elevation column; coordinates only | no unit per variable | a unit and an aggregation period per variable, an elevation in metres per station, and a pressure-reduction convention |
| One comuna key that joins across the files | no -- region only | CUT yes, with 23 rows to re-code | station id only; joins through `emas` | a single post-2018 CUT on all three |
| A time span long enough for a temporal split | 90 days (2026-07-01 .. 2026-09-28) | no -- first-reading dates, not a series | no -- 1 instant | several seasons of the same panel, so a test season is not also the only one |

Only station coverage is answered `yes` by any file, and `rtdata` can confirm it for one instant only. That is the whole finding, in one table: the delivered set is a fire *count* per region-day plus a station *catalogue*, and the measurement that would turn either into a model input -- daily weather at a comuna, on every day, with a unit and a quality flag -- is in none of them.

### What to ask for, in order

1. **An event registry keyed by comuna CUT with a local date.** One row per fire,
   not per region-day: that is the only way the label stops being a counter's
   first difference. The product the plan's Log L5 names is access-gated; nothing
   in these three files substitutes for it.
2. **Daily weather on every day, including quiet ones, at a point in each comuna.**
   Hourly station readings aggregated to a declared civil day, or a reanalysis
   already aggregated -- `meteo.py` shows both shapes. Without the quiet days the
   features exist only where the label is 1.
3. **A declared unit and an aggregation period per variable, and an elevation per
   station.** The snapshot cannot be validated without them, and its pressure
   column cannot be compared across the altiplano and the coast.
4. **A per-reading quality flag with a documented code set.** Two empty columns are
   not a quality signal; they are a schema that was never filled.
5. **The post-2018 CUT on every row, with the region label consistent with it.**
   Otherwise the comuna join that the whole panel and the whole product depend on
   puts stations in the wrong region.

## What this analysis is not

It is not a model, and it does not re-run the rehearsal. `REPORT-delivered-data.md`
records what a model trained on the dashboard scored against climatology; this
report records what the dashboard, the catalogue and the snapshot contain, which is
the prior question. A reader who wants the score reads the other report; a reader
who wants to know which delivered field to repair reads this one.

It is also not a licence review. None of the three files states a licence, a
citation or a retrieval URL, and this report says so rather than assigning one.

The claims above are tested against trimmed fixtures of the same three files under
`backend/training/tests/fixtures/delivered/`, where `PROVENANCE.md` records the
exact selection rule. Those tests change the fixtures and require the numbers to
move, so a number typed into this report instead of computed would fail them.
